# 千牛桌面接入选型

核验日期：2026-09-09。状态：已做首轮本机只读窗口检查，未取得接入兼容性资格。
本记录不授权启用旧 Sidecar、自动发送或改变当前 P1 Gold Conversation Quality 优先级。

## 结论

保留现有 Copilot、聚水潭和货品中心。只评估一个负责会话采集和受控草稿填入的
桌面适配器，不引入其他项目的回复引擎、知识库、Planner 或多 Agent 编排。

当前最小成本顺序是：复用现有 Python/pywinauto 做只读能力探测；只有实际千牛控件
暴露的内容满足身份和会话合同后，才推进接入。若需要独立 Windows 组件，再评估
FlaUI。CDP 是有条件的结构化读取候选，不是未经验证的默认主链路。
UIA、FlaUI、pywinauto 都不需要为控件读取运行视觉模型，但不意味着整套客服免模型用量。

## 附件结论需要纠正之处

1. 不能以名称或 README 证明原版千牛开放标准 CDP。qnbot 的
   [CDPClient](https://github.com/b8vipvip/qnbot/blob/master/src/Bot/ChromeNs/CDPClient.cs)
   接收 SuperWebSocket 会话并处理自定义事件；这不是原版千牛开放 9222 的证明。
2. qianniu-agent 的 [读取实现](https://github.com/tai769/qianniu-agent/blob/master/tools/read_message.py)
   用通用 class 选择器和说话人加内容前缀构造消息标识，取出缓冲列表后只返回第一条。
   这不足以证明连续消息无损、重复短句可区分或多店铺身份隔离。
3. 其 [发送实现](https://github.com/tai769/qianniu-agent/blob/master/tools/send_message.py)
   点击按钮或派发回车即返回成功，不能证明消息进入正确会话，更不能证明客户已收到。
4. UIA 本身就是 Windows 无障碍自动化接口，并非与 Accessibility 独立的第二套兜底。
   能否读取消息取决于目标程序提供的控件/模式；换包装库不能凭空补出缺失数据。
   参见 [Microsoft UI Automation](https://learn.microsoft.com/en-us/dotnet/framework/ui-automation/ui-automation-overview)。
5. 本次没有跨版本、长时负载和升级回归数据，不采用“五星稳定”“后台永远可用”等评级。
   锁屏、RDP 断开和焦点操作都有环境限制，参见
   [pywinauto 远程执行指南](https://pywinauto.readthedocs.io/en/latest/remote_execution.html)。

## 现有代码与可复用边界

- `scripts/sidecar/window_watcher.py`：已有窗口定位/UIA 连接组件，可评估底层复用。
- `scripts/sidecar/uia_sidebar_extractor.py`：读取窗口 Text 后提取订单/商品候选，
  不是经过验收的结构化会话事件源。宽范围文本和正则候选不能直接成为已验证身份。
- `scripts/sidecar/qianniu_sidecar.py`：当前混合采集中，聊天消息由视觉提取填写；
  关闭视觉后 customer_message_source 为 none，不能宣称已具备 UIA 长对话读取。
- 本轮不启用、运行或修复上述旧 Sidecar。用户此前反馈其不可用，需先定位真实能力缺口。

目标职责不变：千牛适配器提供来源明确的店铺、会话、消息和结构化订单引用；现有正式
Pipeline 才负责聚水潭精确身份解析、货品中心事实读取、证据准入、Composer 与安全决策。
接入器不生成客服话术，也不将 UI 展示字段直接批准为事实。既有长对话和产品质量缺陷
不会因为更换接入器自动消失。

## 下一步最小验证建议

1. 只检查用户指定千牛窗口/进程的版本、登录店铺、会话身份、消息角色与顺序。
   不扫描整个桌面，不读取其他应用，不输出原始客户身份和会话，不调用外部模型。
2. 用自有测试会话验证连续三条消息、相同短句、多会话切换、滚动历史、刷新和重连。
   完整性无法证实时报告缺口，不把未暴露历史当成空历史。
3. UIA 缺失必要字段时，才检查该版本是否支持可用且获准的 CDP 连接。
   不抢占其他项目 9222，不开放公网调试端口，不以注入内部 SDK/DLL 作为默认路径。
4. 只读合同通过后再验证草稿填入，校验店铺/会话/请求版本，不能覆盖坐席已有草稿；
   用户切换会话或新增消息使旧候选失效。此阶段不点击发送，can_send 保持 false。
5. 自动发送属于后续单独资格：保留既有 Delivery 决策，校验动作幂等和会话回显，
   发送状态不明时禁止盲目重发。点击成功、输入框清空均不等于送达。

项目许可证、平台使用规则和本机版本兼容性是不同门槛。本次未取得平台对该部署方式
的许可确认，不能承诺不会触发平台限制。当前结果仅支持选型和只读探测，不支持上线。

## 本地结构化预览合同 (2026-09-09)

用户批准了优先级计划中的只读例外；P1 客服质量仍为主线，未晋升多渠道生产接入。
现有 `scripts/sidecar/context_parser.py` 新增纯函数 `build_uia_preview()`，只处理
读取适配器已经划定消息边界的 `qianniu_uia_preview/v1` 输入。输入必须有显式的
当前窗口/会话前后绑定、买家及客服账号元数据、按顺序排列的消息部件和时间。
它不解析整窗文本，不从客户正文猜角色，不证明调用者身份，也不能当作认证 API。

- 调用既有 canonical normalizer 输出 `content`，同时间回合保留原序；重复短句
  不全局去重。末尾买家消息仅从历史尾部移入当前问题，末尾客服消息不触发新问题。
- 窗口/会话变化、未知说话人、空部件、倒序、截断或范围不明均阻断，并清空预览内容。
- 保留所有显式订单与商品编号候选，均为 `verified=false`；不选择第一单，不赋予
  SKU、商品或订单命名空间权威。图片、链接和卡片转为受控 token，不作为商品事实。
- 原始内容仅存在函数返回值的本机内存中，默认对象表示不包含上下文。诊断只有
  计数、角色类型和 reason code。后续外部模型使用仍必须经过既有隐私投影。
- `python scripts/qianniu_sidecar.py --structured-preview-stdin` 从标准输入验证
  一份结构化捕获，只输出诊断 JSON；成功退出 0，阻断退出 2。不启动旧循环、不创建
  日志文件、不打开浏览器、不 POST、不调用模型。该选项默认关闭；不要运行无选项的
  旧脚本来启用本轮能力。此命令不是自动抓取千牛的完整启动器。
- 所有预览 `can_send=false`、`requires_human_review=true`，且
  `should_call_copilot_context=false`。读到历史消息不等于收到新消息。

确定性及关联回归覆盖 84 项测试。再次只读检查同一真实窗口时，聊天文档仍为
147 个后代节点、18 个消息标题，重复读取标题序列不变。依据已确认账号集合只能
关联 17 个标题，另 1 个历史客服样式标题缺少已确认账号绑定。该标题的实际元数据
经标准输入送入本机预览检查后返回 `speaker_unresolved` / 退出 2，无 stderr，
没有将未知角色默认归为客服。这不是全部 18 回合已经成功规范化的结论。

该次合同测试后的剩余接入门槛：原生 UIA 消息/卡片部件生产器、历史客服账号的可靠平台绑定、会话
切换及新消息稳定标识。当前代码验证的是下游预览合同，不是完整原生读取器；没有
启动自动监听或接到正式候选接口。真实数据只在本机内存传递，未写报告、未上传模型，
未修改知识库、聚水潭订单、正式服务、Graph 或发送权限。

## 手动入口实现与最终阻断 (2026-09-09)

复用现有适配脚本、Sidecar Blueprint 和体验台模板，实现了“读取、预览、确认导入”三个
独立动作。`COPILOT_QIANNIU_MANUAL_READ_ENABLED` 默认关闭。POST
`/ask/api/sidecar/qianniu/preview` 只允许直接 loopback、人类身份及既有 CSRF/Origin
校验；公开、转发、共享 public_open 和服务身份均拒绝。单次子进程有 20 秒上限，
不传模型/ERP 凭证，不写日志、旧全局状态或业务库，不触发生成。正常使用要求程序
运行在千牛所在的交互式桌面会话中；本轮受限执行环境曾返回 0 个窗口，不能当作千牛未打开。

原生消息解析复用 `J_msgContainer`、标题的说话人/时间、店铺命名空间和消息部件。
不从正文猜角色，不全局去重，不把客服末句填成新客户问题。图片/链接使用非事实 token；
未知正文节点阻断，不能静默丢失片段。前端必须明确选择窗口、确认预览；取消、换买家、
导入新上下文会使旧异步结果失效，清空原商品/订单/附件/候选；生成仍是独立手动动作。

中间版本实际读取到 18 回合（买家 7、客服 11）、两笔订单及一个产品代码，浏览器确认
导入/换买家流程通过。但复核发现“列表里有同名项”不能证明当前选中，因此该中间结果
**已被替代，不是最终通过结果**。最终实现要求原生选中状态；真实窗口返回：

- UIA 选中买家数 0、选中店铺标签数 0；MSAA 对应选中状态也均为 0。
- 最终返回 `buyer_binding_missing`，不导入上下文，不调用 Agent。
- 多个订单文档直接阻断；当前单个订单文档也没有可证明的买家归属，因此最终原生
  生产器不提供其订单和商品编号候选。`verified=false` 不能替代客户隔离。

选中状态定义依据 Microsoft 的[控件模式属性](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-control-pattern-propids)
与[对象状态常量](https://learn.microsoft.com/en-us/windows/win32/winauto/object-state-constants)，
不是按昵称、商品或案例写规则。没有通过截图颜色或列表顺序猜选中客户。

最终相关 Python 回归 145 项；前端可执行行为测试 22 项。桌面 1280×900、窄屏 390×844
检查了新增弹窗，确认按钮无越界；不是整页移动端适配验收。既有 5012/5174 未修改，
临时 5030 仅用于导入验证，测试后关闭。没有发送真实聊天给外部模型，也没有查询 JST、
写业务库或发给客户。下一门槛是取得真实活动客户及订单面板归属的原生元数据，再做
切换客户负例与一次完整人工复核链路；不能宣布已可生产读取或提高了回答准确率。

## 父控件选择模式复验 (2026-09-09)

在审核队列隔离提交 `8e92ddc` 之后，针对同一用户指定接待窗口复查了父控件选择

无模型/ERP 凭证、无网络请求或消息发送；没有启动完整应用或临时服务器。

| 原生父控件 | UIA Selection | MSAA LegacyIAccessible |
| --- | --- | --- |
| 1 个 Tree | 模式不支持 | 读取成功，选中集合为 0 |
